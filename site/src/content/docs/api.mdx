**In plain words:** an API is the set of addresses the Huddle app talks to behind the scenes, for example to load messages or send one. Developers can use the same addresses to build their own tools. If you just want another tool to post messages into a channel, you don't need this page: use [incoming webhooks](/docs/webhooks) instead.

The rest of this page is for developers. Everything the Huddle app does goes through a JSON API under `/api`. This page explains how it authenticates, how errors look, and lists every route. For posting into a channel from another tool, [incoming webhooks](/docs/webhooks) are the simpler choice.

## How it authenticates

There are no API keys. The API uses the same session cookie as the app:

- **Reading** (`GET`) needs a valid session cookie.
- **Changing anything** (`POST`, `PATCH`, `PUT`, `DELETE`) also needs an `Origin` header equal to Huddle's address. Requests without it are refused with `403`. This is the protection against cross-site request forgery.
- Incoming webhooks and unsubscribe links are the exceptions: their secret token is the credential.

Permissions are the same as in the app: you can only see and do what your role allows (see [People and roles](/docs/roles-and-permissions)).

A script can sign in the way the app does, with an authenticator code, and keep the cookie:

```bash
HUDDLE=https://chat.example.com

curl -c huddle.cookies -X POST "$HUDDLE/api/auth/sign-in/authenticator" \
  -H "origin: $HUDDLE" -H "content-type: application/json" \
  -d '{"email": "you@example.com", "code": "123456"}'

curl -b huddle.cookies "$HUDDLE/api/search?q=invoice&has=file"
```

## Requests and errors

Request and response bodies are JSON, except file uploads (the raw bytes) and file downloads. Errors always have the same shape:

```json
{ "error": { "code": "not_found", "message": "That conversation was not found." } }
```

| Status | Common codes |
| --- | --- |
| `400` | `invalid_request` (the message names the field), `invalid_name`, `not_a_channel` |
| `401` | `unauthorized`: not signed in |
| `403` | `forbidden`: your role doesn't allow it, or the `Origin` is missing |
| `404` | `not_found`: also used for anything you're not allowed to see |
| `409` | `archived`, `name_taken`, `already_member` |
| `413` | `too_large` |
| `429` | `rate_limited`, with a `Retry-After` header |
| `503` | `setup_incomplete`, with the names of the settings to fix |

Paths below are relative to `/api`. "Admin" means owners and admins; "Owner" means the owner only.

### Signing in

| Method | Path | What it does |
| --- | --- | --- |
| `POST` | `/auth/email-otp/send-verification-otp` | Email a sign-in code |
| `POST` | `/auth/sign-in/email-otp` | Sign in with an emailed code |
| `POST` | `/auth/sign-in/authenticator` | Sign in with an authenticator code |
| `POST` | `/auth/authenticator/start` | Start setting up an authenticator app (setup key, invitation, reset link or signed in) |

| `POST` | `/auth/sign-out` | Sign out |
| `POST` | `/setup` | First run: name the workspace (the `ADMIN_EMAIL` account only) |

| `POST` | `/conversations` | Create a channel |
| `POST` | `/conversations/dm` | Open (or create) a DM with these people |
| `GET` | `/conversations/:id` | A conversation and its members |

| `DELETE` | `/conversations/:id/members/:userId` | Remove someone (Admin) |
| `POST` | `/conversations/:id/read` | Move your read marker |
| `PATCH` | `/conversations/:id/notifications` | Your level: `all`, `mentions` or `muted` |

| `DELETE` | `/conversations/:id/messages/:messageId` | Delete a message |

| `POST`, `DELETE` | `/conversations/:id/messages/:messageId/reactions` | Add or remove a reaction |
| `GET` | `/conversations/:id/events` | Events after a sequence number, to catch up |

To send a message, give a `body` and your own `clientMsgId` (8 to 64 letters, digits, `-` or `_`). Sending the same `clientMsgId` again returns the same message instead of a duplicate.

```bash
curl -b huddle.cookies -X POST "$HUDDLE/api/conversations/CONVERSATION_ID/messages" \
  -H "origin: $HUDDLE" -H "content-type: application/json" \
  -d '{"body": "Standup notes are in the doc", "clientMsgId": "script-2026-11-25-001"}'
```

Mentions are written in the body as `<@USER_ID>`, `<@channel>` or `<@here>`.

### Files

| Method | Path | What it does |
| --- | --- | --- |
| `POST` | `/conversations/:id/files` | Upload: raw bytes, name in the `X-File-Name` header (URL-encoded), up to 25 MB |
| `GET` | `/conversations/:id/files` | Files shared in a conversation |
| `GET` | `/files/:id` | Download (add `?inline=1` to view an image or PDF) |

Upload first, then send a message with the file's id in `fileIds`.

### Search

`GET /search` with:

| Parameter | Meaning |
| --- | --- |
| `q` | The words to find (required) |
| `in` | Only this conversation id |
| `from` | Only messages from this user id |
| `has` | `file`: only messages with files |
| `after`, `before` | Dates as `YYYY-MM-DD` |
| `limit` | Up to 50 messages (default 20) |

### Live updates

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | `/realtime/socket` | WebSocket for the sidebar: badge updates |
| `GET` | `/realtime/conversations/:id/socket` | WebSocket for one conversation; `?after=` replays from a sequence number |

Both need the session cookie and Huddle's own `Origin`.

## Incoming webhooks

To post from another tool without signing in, create an [incoming webhook](/docs/webhooks) and call it:

```bash
curl -X POST https://chat.example.com/api/hooks/WEBHOOK_ID/SECRET_TOKEN \
  -H "content-type: application/json" \
  -d '{"text": "Nightly backup finished"}'
```

## Stability

This is the app's own API. Routes can change between versions; check the source in `src/worker/index.ts` and `src/worker/modules` for the version you run.
